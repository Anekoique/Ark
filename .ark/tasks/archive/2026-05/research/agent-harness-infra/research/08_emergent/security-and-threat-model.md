# Security and Threat Model

What Ark assumes about who it's protecting from whom. Most coding agents in 2026 are bimodal — *user-trust-the-agent* (Aider, Cline, Claude Code, Ark) or *run-untrusted-code* (Codex sandboxes, OpenHands Docker, Devin VMs). Ark sits cleanly in the first; this file makes the implicit explicit.

## The two threat models

### Model A — user trusts the agent

- User invokes the agent on their own repo, their own code.
- Agent has read/write access to the workspace and shell access.
- User reviews the diff before commit (or trusts the agent to commit on their behalf).
- Goal: the agent doesn't do something the user wouldn't have approved.

Mitigations needed:
- Approval prompts before destructive operations (Cline, Claude Code).
- Audit log of what was changed (Ark journal, git history).
- Reversibility (every change is a git commit; `git revert` works).

Used by: Aider, Cline, Claude Code, Cursor (default), Continue, **Ark**.

### Model B — run-potentially-untrusted-code

- User submits a task; agent works in isolation; user reviews the output.
- The agent might run code the user didn't author (downloaded from the web, generated by another agent, etc.).
- Goal: the agent's actions can't damage the user's machine, the user's network, or other users.

Mitigations needed:
- OS-level sandbox (Codex Seatbelt / Landlock; OpenHands Docker; E2B Firecracker).
- VM-per-task isolation (Devin).
- Network restrictions (egress filtering, allowlists).
- Credential isolation (per-task tokens).

Used by: Codex (with `--sandbox`), OpenHands (Docker runtime), Devin (VM-per-task), GitHub Copilot Coding Agent (isolated VMs), Replit Agent (sandboxed VMs).

## Ark's chosen position

Ark is unambiguously Model A:

- No OS-level sandboxing.
- Worktrees provide file-path isolation, not process isolation.
- Sub-agent dispatch isolates *context*, not *execution*.
- Hooks run as the user; tool calls run as the user; everything is user-trust.

This is the right model for Ark's primary use case: developers running Ark on their own machines, on their own repos, mediated by Claude Code / Codex / OpenCode (all of which also assume user trust).

The threat model is: "the user might make a mistake; the user might run a misbehaving agent". Mitigations: approval prompts (via host platform), audit logs (journals, git), reversibility (everything in version control).

## What Ark does (and doesn't) protect against

### Protects against

1. **Lost work via accidental overwrite.** Managed-block patterns + the `.installed.json` manifest + `.ark.db` snapshots + git let users recover state. Worst case, `ark remove` + `ark load` restores from snapshot.
2. **Workflow drift between sessions.** Phase forward-only + state-machine validation prevent re-entering completed phases.
3. **Out-of-scope sub-agent writes.** C-28 post-hoc git verification reverts files outside declared scope.
4. **Stale focus / forgotten tasks.** `.state.toml` reconcile-against-disk on every read; corrupted or out-of-sync state is auto-repaired.
5. **Dirty staging at archive.** `ark archive` refuses to run if `git diff --cached` is non-empty.
6. **Corrupt task.toml.** `Error::TaskTomlCorrupt` surfaces a structured error rather than silent failure.

### Does NOT protect against

1. **Malicious agent.** A coding agent told to do something harmful will do it, mediated only by host-platform approval prompts. Ark adds no extra check.
2. **Malicious tools.** MCP servers, slash commands, hooks all run as the user. Ark doesn't sandbox them.
3. **Untrusted code execution.** `ark agent task execute` runs in the user's shell with the user's privileges. Running attacker-supplied code is unprotected.
4. **Credential leakage.** `.env` files in worktrees are visible to all agent activity; secrets aren't compartmentalised.
5. **Network egress.** Agents can make arbitrary HTTP requests; Ark doesn't filter.
6. **Filesystem traversal outside the repo.** Some paths Ark validates (`resolve_safe` for snapshot paths); most agent-driven paths are unchecked.

For Model A this is fine. For Model B Ark would need substantial additions (or to delegate to a Model-B host like Codex with sandboxes).

## Where Ark *could* support Model B without becoming it

A few opt-in additions wouldn't change Ark's primary positioning:

### 1. Codex sandbox profile for EXECUTE

When the user runs Ark on Codex, `task execute --sandbox` could enable Codex's Seatbelt/Landlock profile during the EXECUTE phase. Doesn't change the user-trust default; lets safety-conscious users opt in for safety-sensitive tasks.

### 2. Per-worktree credential scoping

`.ark/worktrees/<branch>/.env` separate from parent's `.env`. Lets users compartmentalise secrets per task. Today the worktree inherits the parent's environment by default; explicit per-worktree env is a config option.

### 3. Subagent tool allow-lists (declarative)

The proposed direction in `claude-code-integration-deep-dive.md` — declare `tools: [Read, Grep, Glob]` for read-only subagents. OS-enforced restriction via host platform's allowlist. Cheap; aligns Model-A trust with Model-B-style guardrails.

### 4. PostToolUse hook for destructive ops

A built-in hook that prompts before `rm -rf`, `git push --force`, `git reset --hard`, etc. Today users rely on the host's hooks; Ark could ship a recommended config.

### 5. Audit-mode `task execute --dry-run`

A mode where EXECUTE prints diffs without applying. Lets users preview agent intentions before committing to filesystem changes. Equivalent to `git diff` before `git apply`.

None of these turn Ark into a Model-B harness; they're trust-deepening features for Model A.

## The 2026 trend

The field is moving toward layered defence:
- **Application layer** (host agent's approval prompts).
- **Workflow layer** (Ark's gates, structured commits).
- **OS layer** (Codex sandboxes, Docker, microVMs).

Ark sits at the workflow layer. The other two layers are owned by the host platform / runtime. The right move is *integrate with them*, not *duplicate them*.

Specifically:
- Codex sandboxes — surface them as an Ark option when on Codex.
- Host approval prompts — let them do their job; don't add a second layer.
- Docker / E2B / Modal runtimes — when users use those, Ark should work cleanly inside them.

## What enterprise / shared-credential environments need

Ark's threat model assumes a single developer on a personal machine. Enterprise environments have additional concerns:

- **Shared credentials.** Multiple developers, one set of API keys. Per-developer attribution becomes important.
- **Audit trails for compliance.** Every agent action logged with developer identity and timestamp.
- **Approval workflows.** Some actions require a second approver.

Ark today has per-developer journals (workspace feature) — partial audit trail. The other concerns are out of scope; they're host-platform / corporate-policy decisions.

If Ark were to broaden to enterprise:
- Per-task `developer_identity` field already exists.
- Cross-task journal aggregation could surface "what did the team do this week".
- Approval workflows would require host-platform cooperation (Cursor's approval prompts, GitHub Copilot's review requirements).

The right move: *don't broaden Ark*; document where enterprise integration plugs into Ark's primitives. Let enterprise users layer policy on top of Ark, not inside it.

## Failure modes

1. **Trust mismatch.** User invokes Ark expecting Model B, doesn't realise it's Model A, runs untrusted code. Mitigation: documentation. Ark's threat model should be explicit.

2. **Sandbox bypass via legitimate tools.** Even with Codex sandbox, `Bash` tool runs in user-space. An agent can write a file containing exploit code, then run it. Mitigation: PostToolUse hooks; sandbox must include the Bash tool's environment.

3. **Credential leakage via prompts.** Agent reads `.env`, content lands in prompt history, ends up in provider logs. Mitigation: redact secrets in tool outputs (host-platform feature).

4. **State file tampering.** User edits `.state.toml` manually with bad values. Ark's reconcile-against-disk pattern detects most cases but not all. Mitigation: more validation in `load_state`.

5. **Worktree pollution across tasks.** Task A's worktree has files left over from task B. Mitigation: clean worktree-creation pattern; `ark cleanup --apply` to remove leftovers.

## Directions for Ark

1. **Document the threat model explicitly.** A `docs/book/src/concepts/threat-model.md` page stating "Ark is a Model-A harness; for Model-B use Codex sandboxes / Docker runtimes / VM hosts". Sets correct user expectations.

2. **Surface Codex sandboxing as an Ark feature.** `task execute --sandbox` on Codex installs maps to the Seatbelt/Landlock profile. Optional; opt-in. Most users won't use it; users who need it have it.

3. **Ship a recommended PostToolUse hook config.** Prompts before destructive operations. Not Ark's enforcement; Ark's *recommendation* shipped as a template.

4. **Per-worktree `.env` opt-in.** Config in `.ark/config.toml` for credential isolation across worktrees. Avoids the "secret in parent leaks to child" pattern.

5. **Subagent `tools` allow-list (already proposed in 06).** Declarative restriction; aligns with the security-deepening pattern without changing the trust model.
